# ADR-0007 — Authentication: Auth.js (next-auth v4) with email magic links and database sessions

Status: Accepted

## Context

The platform needs authenticated identities for every non-public route
(AGENTS §5 S1, ARCHITECTURE §10). The schema already carries `User`,
`Account`, `Session` and `VerificationToken`. HUK wants passwordless sign-in
(email magic link) and a server-side session so that role changes and bans
apply without waiting for a token to expire.

## Decision

- **Library:** Auth.js `next-auth` **v4.24.x** — the current stable release
  (`latest` on npm). Its peer range explicitly supports Next 16
  (`next: ^12.2.5 || ^13 || ^14 || ^15 || ^16`). The v5 line is still
  `5.0.0-beta.32` and is therefore not eligible (pre-release adoption needs an
  owner decision). `next-auth@4.24.15` + `@next-auth/prisma-adapter@1.0.7` +
  `nodemailer@7` were installed.
- **Session strategy: `database`.** The `Session` model exists, and every
  request re-reads the session and the user row (see `src/server/guard.ts`),
  so a role change or a ban takes effect on the next request — verified by
  test. JWT sessions would freeze role/ban state until token expiry.
- **Provider: Email magic link** (nodemailer transport).
  - Development/test: `sendVerificationRequest` prints the link to the
    console (only when `NODE_ENV !== "production"`).
  - Production: SMTP via `EMAIL_SERVER` — required in production by the S8
    env refinement; the URL/token is never logged there.
- **Cookie:** `sessionToken` cookie configured explicitly — `httpOnly`,
  `sameSite=lax`, `secure` (and the `__Secure-` prefix) only in production.
- **Sign-in rate limits:** the H-103 Postgres limiter guards
  `POST /api/auth/signin/email` — 20/hour per hashed client IP and 5/hour per
  hashed email (numbers centralized in `SIGNIN_LIMITS`).
- **Central guard:** `src/server/guard.ts` (`requireSession`, `requireUser`,
  `requireRole`) fails closed (401) on any error while resolving the session;
  banned/deleted users get 403; `ADMIN` satisfies `MODERATOR`.
- **First-admin bootstrap:** optional `INITIAL_ADMIN_EMAIL` — while no ADMIN
  exists, a sign-in with that verified email is promoted to ADMIN, with an
  audit entry (`auth.initial_admin_bootstrap`).

## Consequences

- Roles/bans are enforced live; revoking access is immediate.
- The session lookup adds one indexed DB read per request to protected routes
  (acceptable on a single VPS; cache later if needed).
- `next-auth` v4 is in maintenance mode upstream; migrating to a stable v5
  would be a follow-up naryad (its API for options/adapters differs).
- The Authorization matrix (`tests/authz-matrix.json`) makes every new API
  route declare its access policy or fail CI.
